# AI Coding 的上限，不只由提示词决定

很多人第一次使用 AI Coding 工具时，会自然把它理解成一个更会写代码的聊天框。

你问一句，它答一句；你让它改一个函数，它给你一段 diff；你让它生成脚手架，它吐出一批文件。这个阶段最重要的能力似乎是“会提问”：怎么把需求说清楚，怎么补充约束，怎么让模型不要跑偏。

但用久之后，一个更深的分界会浮出来：真正决定体验上限的，不只是提示词，而是工具如何把命令、上下文、文件编辑、终端执行、验证反馈和可复用技能组织成一个任务系统。

这也是我重新整理 [[ai-coding-agent-tools-map]] 时越来越强的感受。AI Coding 的核心问题，正在从“模型能不能写代码”，变成“一个 agent 能不能稳定进入工程现场，把任务拆开、执行、验证，再把经验沉淀下来”。

本文会借 `claude-code-sourcemap` 这个非官方还原仓库做一个观察样本。需要先说明边界：它不是官方架构文档，也不能被当作 Claude Code 内部实现事实。更稳妥的读法是：公开包、README 和 package 信息展示或暗示了一组产品能力边界，我们可以据此观察成熟 AI Coding CLI 通常会围绕哪些系统问题展开。

## 从聊天框到任务执行系统

如果一个产品只是“能回答编程问题”，它的主要界面就是对话。用户输入问题，模型输出答案，工作基本停在文本层。

但 Claude Code 官方文档和公开包描述指向的是另一类目标：在终端和开发工具中使用 Claude，让它理解代码库、编辑文件、运行命令，并处理开发工作流。这里的关键词不是“回答”，而是“工作流”。

目标一旦从回答问题变成完成任务，系统设计就会被迫改变。

它不只需要语言能力，还需要行动能力：读文件、改文件、执行命令、观察输出、处理错误。它不只要能生成代码，还要知道什么时候先理解仓库，什么时候局部修改，什么时候暂停让用户确认。它也不只是在调用工具，而是在把多步动作组织成可检查的过程。

这时，AI Coding 工具更像一个任务执行系统。聊天仍然存在，但聊天只是入口之一。真正的产品能力，藏在入口之后的组织方式里。

这个判断对用户很重要。因为如果你把它当成聊天框，你会主要优化提示词；如果你把它当成任务系统，你会开始优化任务边界、上下文供给、工具约束和验证闭环。

## 目录名提示的能力分层

`claude-code-sourcemap` 的 README 列出过一组目录名。再次强调，它们只能作为非官方样本观察，不能直接等同于官方内部架构。但这些名称本身很有启发性：

- `commands`
- `tools`
- `services`
- `context`
- `coordinator`
- `plugins`
- `skills`
- `remote`
- `voice`
- `vim`

如果只是围观，`voice`、`vim` 这类词会更吸引眼球。但对重度使用者来说，真正值得盯住的是前半部分：`commands`、`tools`、`context`、`coordinator`、`skills`、`plugins`。

这些词放在一起，暗示了一种和普通聊天产品不同的能力模型。

`commands` 说明任务需要清晰入口。不是所有需求都应该被揉成一段自然语言，有些高频动作会被沉淀成命令，让用户和系统共享一套更稳定的操作语义。

`tools` 说明 agent 不能只靠文本输出。它需要把读文件、写文件、查找、执行、联网、检查状态等能力封装成可调用动作。工具越稳定，模型越容易把意图变成实际改变。

`context` 说明上下文管理是显式产品能力，而不是模型窗口里的自然副产物。系统要决定当前任务该看哪些文件、历史、规则、工具输出和用户约束，也要决定哪些信息应该被裁剪。

`coordinator` 暗示任务执行中可能存在编排层。一个跨文件修改不是一次回答，而是理解、计划、编辑、验证、修正的连续动作。没有编排，工具越多越容易混乱。

`skills` 和 `plugins` 则指向复用和扩展。成熟工作流不能每次都靠模型现场发挥：代码审查、调试、发布、文档整理、测试修复，都应该逐渐形成可复用套路，甚至被外部插件扩展。

这也解释了为什么 AI Coding 工具的差距，不会只体现在同一个问题谁回答得更漂亮。真正的差距会体现在系统是否能稳定处理真实工程任务。

## 提示词仍然重要，但它不是全部

提示词当然重要。模糊的需求会得到模糊的结果，缺失的约束会带来错误的行动。

但在任务执行系统里，提示词只是协作协议的一部分。更关键的是，你能不能用系统能执行、能验证、能回退的方式描述任务。

一个典型反例是这样的请求：

> 帮我把这个项目的登录体验优化一下，顺便看看有没有 bug。

这句话作为聊天起点没问题，但作为执行任务太松。它没有说明要先分析还是直接修改，没有限定范围，没有定义成功标准，也没有告诉 agent 哪些命令能证明改动可用。

更适合 agent 的写法会把工作拆开：

1. 先阅读登录相关路由、组件和测试，不要修改文件。
2. 总结当前流程和明显风险，列出最多三个改动方案。
3. 只实现确认后的一个方案，限制在登录模块内。
4. 修改后运行指定测试和类型检查。
5. 如果验证失败，先报告失败原因，再决定是否继续修。

这不是“提示词技巧”意义上的华丽表达，而是在给任务系统提供执行边界。你不是要求它“更仔细”，而是在规定它怎样行动、怎样停止、怎样证明。

对复杂系统来说，这比“请认真一点”“不要出错”更有用。态度词很难落到工具层，边界和验证命令可以。

## 上下文是产品，不是副作用

AI Coding 的许多失败，看起来像模型不够聪明，实际上是上下文组织失败。

同一个模型，在不同工具里的表现可能差很多。原因不一定是模型本身变了，而是产品在不同时间把不同材料送进了模型：项目结构、当前文件、相关实现、测试输出、历史对话、用户偏好、仓库约定、错误日志。

上下文不是“多塞一点资料”这么简单。它至少包含四个判断：

1. 当前任务真正需要哪些材料。
2. 哪些材料虽然相关，但会制造噪声。
3. 哪些历史约束必须保留。
4. 哪些工具输出应该被转成下一步行动依据。

例如，一个 agent 要修复测试失败，最需要的可能不是整个代码库，而是失败日志、相关测试、被测函数、最近改动和项目测试约定。如果系统把大量无关文件塞进上下文，模型会分心；如果系统漏掉失败日志，模型会凭空猜测。

这就是为什么上下文层应该被当作产品能力看待。它决定 agent 看见什么，也决定它误解什么。

长期记忆是上下文问题的延伸，但不是同一件事。上下文解决“这一次任务要看什么”，记忆解决“以后不要忘什么”。比如项目偏好、历史失败方案、维护者约束和反复出现的工作模式，更适合进入长期记忆层。关于这点，我在 [[hindsight-agent-memory]] 里单独写过。

## 工具越多，越需要约束

很多人期待 AI Coding 工具拥有更多能力：能读文件，能改文件，能跑测试，能查文档，能开浏览器，能发 PR。这个方向是对的，但它也带来一个容易被忽略的问题：工具越多，越需要边界。

一个只能回答文本的模型，最多给你错误建议。一个能修改仓库、执行命令、触发外部系统的 agent，如果没有约束，错误会直接进入工作现场。

所以成熟使用方式不是“放开让它做”，而是让工具能力进入可控流程：

- 读取阶段只读不写。
- 修改阶段限制文件范围。
- 执行命令时明确验证命令和禁止动作。
- 遇到不确定事实时回到来源，而不是补全想象。
- 涉及发布、提交、推送、凭据、生产环境时要求显式确认。

这类约束看起来繁琐，但它们正是任务系统可用的基础。AI Coding 的目标不是让 agent 永远自由发挥，而是让它在合适的轨道里承担更多执行工作。

从这个角度看，好的 agent 协作不是把人排除出去，而是重新分配人和系统的责任：人定义目标、边界和风险承受范围；agent 负责检索、修改、验证和汇报；验证结果再把人带回决策点。

## 技能和插件让经验可以复用

当一个工作流反复出现，它就不应该永远停留在临时提示词里。

比如代码审查、调试、前端视觉验收、发布前检查、长文改写、知识库公开构建，这些任务都有稳定步骤。每次都靠用户从头描述，不仅低效，也容易遗漏关键环节。

这就是 `skills` 和 `plugins` 这类机制值得关注的原因。它们暗示 AI Coding 工具正在把“怎么做一类任务”从一次性对话中抽出来，变成可复用的操作资产。

临时提示词像手写便签，技能和插件更像团队流程。前者适合探索，后者适合沉淀。

对个人用户来说，这意味着可以把自己的高频协作方式逐渐结构化：如何让 agent 读项目规则，如何要求它先给计划，如何验收前端页面，如何构建公开内容，如何在失败后复盘。对团队来说，这进一步变成工程规范：哪些命令能跑，哪些目录不能碰，哪些改动必须先请求确认，哪些验证不能跳过。

这也是 AI Coding 工具从“聪明助手”走向“工程系统”的关键一步。模型输出会波动，但流程资产可以积累。

## 验证闭环决定结果能不能落地

AI Coding 最容易制造错觉的一点，是它几乎总能写出点什么。

但真实工程不奖励“写出点什么”。真实工程只关心改动能不能通过类型检查、测试、构建、人工审查和运行时验证。

所以，在真正进入工程现场的 AI Coding 流程里，验证应该成为任务闭环的一部分。

一个可靠的任务循环通常长这样：

1. 先理解任务和仓库约束。
2. 再制定有限计划。
3. 然后执行最小必要修改。
4. 接着运行验证命令。
5. 根据验证输出修正或停止。
6. 最后报告改了什么、证据是什么、还剩什么风险。

这里最重要的不是“agent 会不会说自己完成了”，而是它能不能拿出可检查的证据。测试输出、构建结果、静态检查、截图、diff、日志，都是把语言承诺拉回工程现实的方式。

重度用户最终追求的不是“一次性帮我做完”，而是“进入我的开发闭环”。这两者差别很大。前者容易鼓励过度自信，后者要求每一步都能观察、能中断、能回退。

## 用户应该怎样升级协作方式

如果把 AI Coding 工具理解成任务执行系统，用户的最佳实践也会随之变化。

第一，先定义任务阶段。不要把探索、方案、执行、验证、发布混在一个请求里。阶段越清楚，agent 越容易选择正确工具。

第二，给出动作边界。与其说“别乱改”，不如说“这轮只读不写”“只改这个文件”“不要提交”“验证失败先停下来报告”。

第三，提供可验证标准。告诉 agent 哪些命令、页面、测试或输出能证明任务完成。没有验证标准，agent 很容易把“文本上解释通了”误当成“工程上完成了”。

第四，把反复出现的协作方式沉淀下来。如果你总是在同类任务里写同样的提示，那它很可能应该变成模板、技能、项目规则或自动化脚本。

第五，区分私有探索和公开输出。个人知识库、草稿、内部判断和公开页面不应混为一谈。AI 可以帮助整理，但公开边界仍然要由明确规则控制。

这些做法看起来不像传统意义上的“prompt engineering”。它们更接近 workflow engineering：设计任务如何进入系统，如何被执行，如何被证明，如何留下经验。

## 重新理解 AI Coding 的上限

过去我们很容易把 AI Coding 工具的进步归因于模型更强：代码能力更好，推理更稳，上下文窗口更长。

这些当然重要。但它们不是全部。

一个成熟 AI Coding 工具的上限，还取决于系统组织能力：

- 命令入口是否清晰。
- 工具层是否稳定。
- 上下文管理是否聪明。
- 任务编排是否自然。
- 技能和插件是否能沉淀经验。
- 验证闭环是否可靠。
- 人和 agent 的责任边界是否明确。

模型像发动机，但 AI Coding 产品不是一台裸发动机。它还需要方向盘、仪表盘、刹车、传动系统、维修手册和驾驶规则。真正影响使用体验的，往往是这些部件如何协同。

`claude-code-sourcemap` 这类非官方材料的价值，不在于把目录名当作谈资，也不在于把它当作官方内部图纸。更有价值的读法是：把它当作一个公开样本，观察一个面向真实开发任务的 CLI agent 可能需要哪些层次。

从这个角度看，未来 AI Coding 的高手未必只是最会写提示词的人。更可能是最懂得设计任务、组织上下文、约束工具、沉淀技能并坚持验证闭环的人。

也就是说，AI Coding 的上限，不只由提示词决定。它由整个任务系统决定。
