# Agent CLI 真正难的不是接模型，而是工程组织

如果你是做工程平台、CLI 或 Agent 产品的开发者，看 `claude-code-sourcemap` 这类材料时，最值得关注的不是“还原了多少包结构”，也不是某个目录名是不是暗示了某个新功能。

更有价值的问题是：一个现代 AI Coding Agent CLI，为什么会需要这样的工程分层？

这里先把边界说清楚。`claude-code-sourcemap` 是一个基于公开 npm 包和 source map 的非官方还原项目，不是 Claude Code 的官方架构文档，也不能被当成 Anthropic 内部仓库结构的直接证明。它的价值更像一个公开样本：让我们从包结构、目录名和公开描述里，观察一个 Agent CLI 可能需要处理哪些系统问题。

这篇文章讨论的也不是“Claude Code 官方架构是什么”，而是借这份非官方材料梳理一个更通用的判断：做 Agent CLI，难点通常不在“把请求接到模型 API 上”，而在如何把模型能力组织成一个可扩展、可验证、可交互、可维护的系统。

这个判断也可以放回更大的工具地图里看：[[ai-coding-agent-tools-map]]。模型只是其中一层，真正决定长期体验上限的，是模型之外的命令、工具、上下文、编排、扩展和验证机制。

## 先看到分层，而不是功能猜测

`claude-code-sourcemap` 的 README 列出了一批很有信息量的目录名，包括 `main.tsx`、`commands`、`tools`、`services`、`utils`、`context`、`coordinator`、`plugins`、`skills`，以及 `remote`、`voice`、`vim` 等。[README](https://raw.githubusercontent.com/ChinaSiro/claude-code-sourcemap/main/README.md)

这些名字本身不能证明某个具体实现细节，但它们组合在一起时，已经足够提示一种工程组织方向：

- `main.tsx` 更像入口与交互外壳
- `commands` 更像用户可触发的任务入口
- `tools` 更像系统内部可调用的原子能力
- `services` 更像运行支撑层
- `context` 更像会话、状态和材料组织层
- `coordinator` 更像任务编排层
- `plugins` 和 `skills` 更像扩展与经验复用层

这套分层背后最重要的启发是：不要把 Agent 写成一个越来越大的单循环。

很多团队刚开始做 Agent CLI 时，最自然的做法是把所有事情放在一条主流程里：收用户输入，拼 prompt，调用模型，解析工具请求，执行工具，再把结果塞回上下文。这个结构在原型阶段非常快，因为每加一个能力只要往循环里再塞一段逻辑。

问题是，Agent CLI 面对的不是单次问答，而是一段持续变化的任务过程。用户会补充目标，代码库会变化，工具执行会失败，权限会被拒绝，测试会返回新线索，模型也可能需要在“探索、修改、验证、总结”之间切换策略。

如果所有逻辑都堆在一个循环里，早期速度会变成后期负债。调试时很难判断是哪一层出了问题，扩展时很难只替换其中一个部件，验证时也很难把模型决策、工具执行和任务状态分开看。

所以，成熟 Agent CLI 的关键不是让用户看到很多复杂层次，而是让内部边界足够清楚：用户体验可以是一条连续对话，工程实现却必须拆成多个可理解、可替换、可检查的层。

## `commands` 是任务入口，`tools` 是能力底座

`commands` 和 `tools` 的区分，是这类系统里最值得重视的一层。

表面看，命令和工具都在“做事”。但如果把它们混成一层，系统很快会遇到两个问题：产品入口越来越乱，底层能力也越来越难复用。

`commands` 更靠近用户心智。它决定用户怎样进入任务：是让 Agent 解释一段代码，还是让它修一个测试，还是让它审查一个 diff，或者初始化一个项目规则。命令层需要考虑的是任务命名、参数、确认流程、帮助信息、失败反馈，以及用户是否能预测这个命令会做什么。

`tools` 更靠近执行能力。它们通常是 Agent 在任务过程中调用的原子动作：读取文件、搜索文本、编辑文件、运行命令、检查 git 状态、访问外部服务，或者调用某个专门协议。工具层关心的是输入输出协议、权限、安全边界、错误处理、可观测性和可测试性。

这两个层次的生命周期也不同。

一个新工具不一定需要立刻呈现给用户。比如系统增加了更好的文件搜索能力，可能只是让现有“修复 bug”命令更稳定，而不需要新增一个用户可见命令。反过来，一个新命令也不一定需要全新的底层工具，它可能只是把已有工具按更合理的顺序组织起来。

这种解耦会直接影响长期维护。没有命令层，用户只能面对能力碎片；没有工具层，系统只能把每个任务写成一段不可复用的流程。对 Agent CLI 来说，好的设计通常是：命令负责表达任务意图，工具负责提供稳定能力，中间再由编排层把二者连接起来。

从官方文档和公开包描述看，Claude Code 被描述为一个能理解代码库、编辑文件、运行终端命令并处理开发工作流的工具。这样的产品目标天然要求系统同时处理“用户任务入口”和“底层执行能力”。如果这两层不分开，工作流越完整，耦合就越严重。

## `context` 不是 prompt 拼接，而是系统基础设施

很多 Agent 早期失败，不是因为模型完全没有能力，而是因为上下文组织太随意。

传统 CLI 的核心路径很清楚：输入参数，执行程序，输出结果。Agent CLI 不一样。它不仅要处理当前输入，还要处理任务历史、仓库状态、用户偏好、工具结果、约束规则、未完成计划，以及哪些信息应该继续保留、哪些信息应该被压缩或丢弃。

如果没有正式的 `context` 层，这些东西往往会退化成一段不断膨胀的 prompt 拼接逻辑。短任务时还能工作，任务一长就会出现问题：

- 重要约束被冲掉，模型开始忽略早期规则
- 工具输出原样堆积，信噪比越来越低
- 旧计划和新目标混在一起，执行方向变形
- 文件、测试、用户意图之间缺少稳定引用关系
- 排查错误时无法判断模型到底看见了什么

把上下文当成工程对象，意味着要为它设计结构，而不是只把文本塞进窗口。至少需要回答几个问题：当前任务目标是什么？哪些材料是事实来源？哪些是模型推断？哪些状态来自工具执行？哪些内容可以被压缩？哪些内容必须原样保留？哪些上下文应该进入下一轮，哪些应该被隔离在本轮？

这也是为什么 `context` 这类目录名值得注意。它提示我们，Agent CLI 的上下文不是“聊天记录”那么简单，而更像系统运行时的工作内存。模型每次调用只是其中一个瞬间，真正让任务连续起来的是上下文层。

对工程团队来说，这里最容易犯的错，是把上下文优化理解成“塞更多材料”。更稳的方向是“让材料有结构、有来源、有生命周期”。能塞进更多 token 不等于更理解任务；能在正确阶段提供正确材料，才是 Agent CLI 的核心能力。

## `coordinator` 处理的是任务状态机

如果说 `context` 解决“系统知道什么”，那么 `coordinator` 解决“系统下一步做什么”。

Agent CLI 的复杂度，往往来自任务不是一步完成的。一个看似简单的“修复这个失败测试”，实际可能包含多轮状态变化：读取错误，定位相关文件，提出假设，修改代码，运行测试，发现新失败，缩小范围，再次修改，最后总结变更。

这里的关键不只是模型会不会推理，而是系统有没有一个明确的编排位置来管理这些阶段。

没有编排层时，所有决策都会挤进模型回复和工具调用之间：什么时候继续探索，什么时候开始修改，什么时候必须先问用户，什么时候应该停止，什么时候需要验证，什么时候该回滚或换方案。这种隐式状态机很难维护，也很难测试。

`coordinator` 这类层次的意义，是把任务过程变成可管理对象。它可以负责：

- 把用户目标转成阶段性计划
- 决定什么时候调用哪些工具
- 在工具失败时选择重试、降级、询问或停止
- 管理验证步骤和完成条件
- 把中间结果写回上下文
- 在长任务中控制节奏和风险

这不意味着所有 Agent 都必须有一个叫 `coordinator` 的目录。名字并不重要，重要的是职责不能消失。只要系统开始处理跨文件修改、命令执行、测试验证和多轮协作，就一定会出现任务编排问题。

很多人以为自己在优化模型，其实真正需要优化的是任务状态机。模型可以给出建议，但系统要决定建议如何落地、何时验证、失败后怎样恢复，以及怎样把过程变得可观察。

## `services` 和 `utils` 是稳定运行的支撑层

相比 `commands`、`tools`、`context`、`coordinator`，`services` 和 `utils` 看起来没那么有话题性。但从工程角度看，它们经常决定一个 Agent CLI 能不能长期稳定运行。

Agent CLI 不是一个纯文本生成器。它会接触文件系统、终端、网络、配置、鉴权、日志、缓存、更新机制、遥测、权限确认和错误恢复。这些能力如果散落在各个命令和工具里，系统很快会出现重复实现和行为不一致。

`services` 更适合承载横向基础设施。例如配置读取、会话存储、进程管理、外部 API 客户端、权限策略、日志记录和指标采集。它们不一定直接呈现给模型，也不一定直接对应用户命令，但会影响每一次工具调用和任务执行。

`utils` 则更适合放纯函数和小型辅助逻辑。这里的风险是边界滑坡：一开始只是工具函数，后来塞进隐含状态、外部副作用和业务规则。长期看，凡是涉及运行状态、外部资源或安全边界的逻辑，都不应该悄悄躲在 `utils` 里。

这层的工程价值在于一致性。一个 Agent CLI 如果既能改文件又能跑命令，就必须让权限提示、错误格式、超时处理、日志记录和用户反馈尽量一致。否则用户会感觉自己面对的不是一个系统，而是一组拼在一起的脚本。

## `plugins` 扩展系统能力，`skills` 复用任务经验

任何 Agent 产品，只靠内置能力都会很快遇到天花板。不同团队有不同代码库，不同语言栈有不同工具链，不同用户也有不同工作习惯。把所有能力都写进主程序，最后会让核心系统越来越重，也越来越难保持清晰。

这就是 `plugins` 和 `skills` 值得单独讨论的原因。它们都指向扩展，但扩展的对象不同。

`plugins` 更像系统级扩展机制。它关心的是如何把新能力接进 Agent CLI：新的工具、新的外部服务、新的运行环境、新的认证方式、新的 UI 表面，或者团队内部系统的集成。插件机制需要非常重视边界，因为它一旦允许外部能力进入系统，就会带来权限、安全、版本兼容和故障隔离问题。

一个插件系统至少要回答：插件能注册什么？能访问哪些上下文？能调用哪些工具？失败时是否影响主流程？如何声明权限？如何升级和禁用？如何让用户知道某一步来自内置能力还是插件能力？

`skills` 更像经验级扩展机制。它关心的不是“接入一个新 API”，而是“把某类任务的做法沉淀下来”。例如代码审查应该先看哪些文件，调试失败测试应该按什么顺序收集证据，写公开文章应该怎样处理来源和私有边界，发布前应该跑哪些验证命令。

换句话说，plugin 偏能力，skill 偏方法。plugin 让系统能做更多事，skill 让系统以更稳定的方式做某类事。

这层设计很关键，因为 Agent 的一个核心问题是任务方差太大。同一个目标，不同轮次可能走出完全不同的路径。把经验沉淀为 skill，本质上是在把“临场发挥”压缩成“可复用流程”。这不会消除模型的不确定性，但可以显著降低重复犯错的概率。

真正成熟的 Agent CLI，应该允许系统能力和任务经验分别演进。团队增加一个内部部署工具，不应该重写所有任务流程；团队沉淀一套代码审查方法，也不应该必须改动底层工具实现。

## `remote`、`voice`、`vim` 可能提示多交互表面

`remote`、`voice`、`vim` 这些目录名很容易引发产品路线联想。但基于非官方还原材料，最好不要把它们写成已经确认的路线或功能承诺。更稳妥的说法是：它们可能提示 Agent CLI 需要面对多种交互表面。

如果一个系统不只存在于本地终端，而可能进入远程会话、语音入口或编辑器工作流，工程挑战就会从“多几个功能点”变成“同一个任务内核如何适配不同表面”。

这里真正值得关注的是一组系统问题：

- 状态能否跨交互表面保持一致？
- 远程环境和本地环境的权限模型是否相同？
- 语音输入带来的不确定性如何进入确认流程？
- 编辑器里的局部上下文如何和 CLI 的全局任务状态合并？
- 同一个工具调用结果，如何在文本、语音或编辑器 UI 中以合适方式呈现？
- 用户在一个表面中中断任务，能否在另一个表面里恢复？

这些问题会倒逼系统把“任务内核”和“交互表面”分开。CLI 可以是一种入口，编辑器可以是一种入口，远程或语音也可以是入口；但任务状态、上下文、工具权限、验证条件和完成定义，最好不要被写死在某一种入口里。

这对正在做 Agent 产品的团队很重要。早期只做终端时，很容易把所有交互假设都写进命令行流程里。等到需要接编辑器、远程执行或其他输入方式时，才发现任务逻辑和 UI 表面已经绑死。到那时再拆，会比一开始保留边界困难得多。

## 验证能力必须进入系统设计

Agent CLI 和普通聊天机器人的一个重要差别，是它会改变外部世界：改文件、运行命令、提交补丁、调用服务。只要系统能行动，验证就不能只是用户手动补上的最后一步。

一个只会执行的 Agent，很容易成为错误放大器。它可以快速生成大量改动，也可以快速把错误假设写进多个文件。真正可用的系统，必须能把“执行”和“验证”放在同一个任务闭环里。

验证层至少包括几类能力。

第一是命令级验证。系统要知道哪些任务完成后应该跑哪些检查，比如语法检查、单元测试、构建、格式化、类型检查或专门的回归命令。

第二是状态级验证。工具执行是否真的成功？文件是否按预期改变？工作区是否出现未计划的改动？生成物是否进入了不该进入的目录？

第三是语义级验证。任务是否仍然满足用户目标？是否引入了新的约束冲突？是否把非公开内容带进公开输出？这类验证不能完全依赖编译器，需要规则、上下文和人工确认共同参与。

第四是交互级验证。高风险操作前是否需要确认？失败后是否向用户解释了可选路径？长任务中是否持续报告状态？用户修正目标后，系统是否真的更新了计划？

这也是为什么 Agent CLI 的工程组织不能只围绕模型调用来设计。模型负责提出和选择动作，但系统必须给动作提供边界、证据和退出条件。

## 如果你也在做 Agent CLI，优先盯住这些边界

从这份非官方样本出发，我会把 Agent CLI 的工程优先级排成几条更朴素的原则。

第一，先做边界，再堆能力。命令入口、工具接口、上下文结构、编排职责、权限模型和验证机制，要比“再加一个工具”更早稳定下来。边界不清楚时，能力越多，系统越难维护。

第二，把上下文当成基础设施。不要把上下文写成几个散落函数，也不要把历史直接堆成一个巨大 prompt。上下文应该有结构、来源、生命周期和可检查性。

第三，把编排层显式化。只要任务包含多步执行，就需要有人管理阶段、失败、重试、确认和完成条件。这个职责可以不叫 coordinator，但不能消失。

第四，把扩展拆成能力扩展和经验扩展。插件解决“系统还能接入什么”，技能解决“某类任务应该怎么做”。两者混在一起，会让扩展机制既难管权限，也难复用方法。

第五，把验证流程内建进去。Agent 不应该只会生成行动，还应该知道何时检查行动结果、如何解释失败，以及什么时候必须停下来等用户判断。

第六，保留交互表面的可替换性。今天是 CLI，明天可能是编辑器、远程会话或其他入口。任务内核如果从第一天就被某个界面绑死，后续扩展会非常痛。

这些原则听起来不像模型能力展示那么惊艳，却更接近真实产品的难处。接模型 API 是起点，组织模型能力才是系统工程。

## 把非官方样本当作工程参照，而不是权威答案

最后仍然要回到边界：`claude-code-sourcemap` 不是官方架构文档。它基于公开包和 source map 做还原，README 也说明其不代表官方原始仓库结构。[README](https://raw.githubusercontent.com/ChinaSiro/claude-code-sourcemap/main/README.md)

所以，最好的阅读方式不是把每个目录名当成确定事实，而是把它当成一个工程参照：一个现代 AI Coding Agent CLI，可能需要怎样的层次，哪些职责最好不要混在一起，哪些扩展点应该尽早设计边界。

如果只看模型，Agent CLI 像是一个更会写代码的终端聊天框。顺着 `commands`、`tools`、`context`、`coordinator`、`plugins`、`skills` 这些层次看，它更像一套围绕模型组织起来的任务系统。

真正困难的地方也就在这里：让模型能回答问题并不稀奇，让模型能力在复杂工程任务里稳定、可控、可验证地工作，才是 Agent CLI 的核心竞争力。
