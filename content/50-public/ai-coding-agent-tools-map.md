# AI Coding 和 Agent 工具：一张个人知识库里的工具地图

AI Coding 工具很容易被混成一团：新模型、编辑器插件、CLI agent、上下文检索、长期记忆、自动发布流程，都被放进同一个“提升效率”的篮子里。

但在真实工作流里，它们解决的不是同一个问题。把这些工具分层管理，是为了避免每次选型都从“哪个工具最强”开始，而是先问：当前卡住的是哪一层？

这页是一张个人知识库里的工具地图，不是长篇评测。它的目标是给后续笔记、实验和公开文章一个稳定索引。

## 为什么要分层

**模型层变化最快。**
模型决定基础能力、价格、速度、上下文窗口和多模态能力。但模型能力更新太快，如果把整个工作流都绑定在某一个模型上，知识库很快会过期。更稳的做法是把模型视为可替换能力源，而不是工作流本身。

**编辑器和 CLI 层决定操作入口。**
同一个模型放进编辑器、终端、Git 工作流或代码审查流程，体验完全不同。编辑器更适合局部补全、重构和阅读；CLI agent 更适合跨文件修改、运行测试、处理仓库任务。这里要管理的是“人和 agent 怎么协作”，不是单纯比较回答质量。

**上下文层决定 agent 看见什么。**
AI Coding 的很多失败不是因为模型不会写，而是因为它没有看到约束：项目结构、测试命令、架构决策、已有实现、团队约定。上下文层要回答的是：这一次任务需要哪些材料，如何稳定、可审计地送到模型面前。

**记忆层决定历史能不能留下来。**
上下文解决“这一次要看什么”，记忆解决“以后别忘什么”。项目偏好、踩坑记录、失败方案、维护者约束和长期工作习惯，都不应该每次开新 session 重新解释。关于这层，我单独整理过一篇：[[hindsight-agent-memory]]。

**发布流程层决定哪些内容可以公开。**
个人知识库里会同时存在原始材料、草稿、内部判断和公开笔记。AI agent 可以帮助整理，但不应该替人越过审核边界。发布流程层要管理的是 frontmatter、公开标记、私有片段清理、链接检查和最终输出。

## 工具地图

| 层级 | 关注问题 | 常见工具形态 | 应该沉淀什么 |
| --- | --- | --- | --- |
| 模型 | 哪个能力源适合当前任务 | 通用大模型、代码模型、多模态模型、本地模型 | 能力边界、价格/速度经验、适用场景 |
| 编辑器 / CLI | 人和 agent 在哪里协作 | IDE 插件、终端 agent、代码审查助手、自动化脚本 | 常用命令、任务模板、失败恢复方式 |
| 上下文 | 这次任务需要哪些材料 | 仓库索引、文件检索、RAG、规范文档、任务计划 | 项目约束、架构入口、测试入口、相关笔记 |
| 记忆 | 哪些经验要跨 session 保留 | 长期记忆系统、项目日志、偏好记录、决策记录 | 踩坑记录、稳定偏好、历史决策、反复出现的模式 |
| 发布流程 | 什么可以从私有库进入公开库 | Markdown frontmatter、公开构建脚本、私有块标记、Quartz 页面 | 发布规则、公开索引、来源追踪、审核清单 |

## 使用顺序

一个实用的判断顺序是：

1. 先确认任务类型：写代码、读代码、重构、调试、写作、发布，分别需要不同入口。
2. 再选操作入口：小范围编辑优先编辑器，跨文件任务优先 CLI agent，知识整理优先从笔记结构开始。
3. 然后补上下文：把相关代码、规则、历史决策和测试命令放进任务边界。
4. 如果问题会反复出现，再沉淀为记忆：不要把每次临时提示都当成长期规则。
5. 最后才进入发布流程：只有明确标记为公开、并经过清理的内容，才进入公开输出。

这套顺序的好处是，它把“试工具”变成“维护系统”。模型可以换，编辑器可以换，CLI 可以换；但只要分层清楚，个人知识库里的经验就不会跟着工具热度一起散掉。
